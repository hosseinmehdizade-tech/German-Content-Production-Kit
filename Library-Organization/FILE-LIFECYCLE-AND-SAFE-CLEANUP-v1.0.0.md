# Global File Lifecycle & Safe Cleanup Contract v1.0.0
**Status:** ACTIVE USER DIRECTIVE — prospective, all content-workstream projects, 2026-11-06.
**Authority:** This contract governs file creation, retention, candidate detection and user-authorized Library deletion. It is subordinate to SOURCE/LOCKED integrity, active source-specific checkpoint authority, existing Library direct-save/routing rules and Git synchronization; it never grants Stage4/5/6/7 approval, app migration or changes to learner data.

## Must run without a user reminder
Apply this contract when starting/resuming **every** current/future workstream, before saving a new Library file, when a lesson or production milestone finishes, and whenever a file is replaced. Do not ask the user to prompt cleanup. The agent/process proactively identifies superseded or duplicate candidates and reports a short cleanup summary **in the normal milestone handoff**; no dedicated report/ZIP/PR just to say a file exists.

## One owner, one active artifact per unit (where sufficient)
1. Resolve actual project owner and its existing Library folder with `Library-Organization/CONTENT-PROJECT-FOLDERS.json` and `LIBRARY-DIRECT-SAVE-ENFORCEMENT-v1.1.0.json`. Check nested workstreams: do not mix Aspekte B1+/B2/C1, Menschen levels, NVV, app runtime or shared user sources. Never save to generic Library root merely for convenience.
2. Reuse the existing **current** lesson bundle/canonical working JSON and append deltas when safe; avoid successive full ZIP snapshots after each tiny edit. At a meaningful checkpoint prefer (a) one current lesson/content bundle and (b) a compact QA/decision receipt; retain extra immutable source/evidence only when needed for exact reconstruction.
3. Classify each new and existing touched artifact: `SOURCE_PROTECTED`, `FINAL_PROTECTED`, `CURRENT_ACTIVE`, `RECOVERY_CHECKPOINT_PINNED`, `HOLD_UNRESOLVED`, `TEMP_ACTIVE`, `SUPERSEDED_CANDIDATE`, `EXACT_DUPLICATE_CANDIDATE`, `DELETE_APPROVED`, `DELETED_OR_TRASHED`. A historical WIP name alone **never** proves supersession.
4. At every **validated milestone**, maintain a compact `artifact_lifecycle` record inside the existing per-project `CHECKPOINT.json` or `LATEST.json` if its schema safely accepts additive metadata. Otherwise keep **one** `ARTIFACT-REGISTER.json` per owner, not one report per file. Store: `owner`, `lesson_or_stage`, `name`, `library_file_id` (or exact current file_id), `library_path`, `sha256`, `bytes`, `created_or_updated_at`, `status`, `supersedes_ids`, `depends_on_ids`, `recovery_copy_id`, `decision_reason` and `source_or_release_authority`. Missing fields are `UNVERIFIED`, not invented.
5. Only after exact provider Library write/readback is a file called saved. A sandbox path, user-visible chat attachment or Git commit is not itself a Library save. Git carries slim identities and handoff metadata; private bulk source stays in its authorized storage.
6. At each milestone, derive a cleanup candidate list from newly superseded artifacts and exact duplicates. Include exact IDs, canonical retained copy, content hashes, dependency and source pointers, per-item size and aggregate **nominal** reclaimable bytes. Put a succinct status in the normal lesson handoff, not a forest of checkpoints.

## Safe cleanup (strict fail-closed)
- **Never delete automatically** from a general preference to keep Library tidy. The user's general approval of this contract authorizes proactive **inventory and proposals**, not deletion of unidentified files. A deletion batch requires explicit user authorization identifying its scope/entries; reuse existing approval only for those exact entries.
- Delete or move only by exact current Library IDs. Compare independent raw SHA-256 of both full files and validate ZIP CRC/manifest where applicable before claiming an exact duplicate; identical names, sizes, dates, visual appearance, or filenames suffixed `(1)` are insufficient.
- Independently check SOURCE, FINAL, LOCKED, actively referenced CURRENT/Checkpoint/Stage5/Stage6, unresolved HOLDs, sole available recovery copies, historical Git pins, cross-project dependencies and required backups. If uncertain, `HOLD_NO_DELETE`; optionally offer an archive **after** scope approval.
- Choose a single authoritative retained file with stable ID, hash and a verified retrieval path. Do not rewrite source-owner authority or silently substitute a duplicate's ID for historical Git records. Post-delete re-list both affected owner paths; verify every protected retained ID remains. Report actual deleted IDs and bytes. **Trash may retain storage usage:** never claim quota space truly reclaimed without storage evidence.
- Project attachments, Library files, Git blobs/releases, external Drive backups and chat downloadable sandbox files have different deletion capabilities. A Library deletion does **not** remove project attachments, Git history, chat history or connected Drive originals.
- If the provider refuses deletion or precondition is unverified: stop and report blocker. No destructive fallback, no speculative bulk delete, no auto-Git governance rewrites.

## Project-local adoption and future workspaces
Every existing `Workspaces/<slug>/` contains `FILE-LIFECYCLE-RULE.md` linking here. Every newly created workstream **must create the same project-local link at initialization**. At resume, read the local link and this contract alongside the active checkpoint; run proactive candidate identification after each meaningful deliverable. Content Library folders are mapped in `CONTENT-PROJECT-FOLDERS.json`; no orphan project or content family is exempt.

**No automatic background operation is promised:** this contract is automatically applied whenever a workstream is actively processed by an assistant/runner. Outside an active run, monitoring or scheduled cleanup requires a separately configured automation.
