# Dynamic Content Portfolio — Operating Contract v1

**Program:** Continuous Optimization Program / Project Control Center. **Scope:** the 10 user-selected content families, as a subset of the existing 21-family catalog. **As-of seed:** 2026-11-07.

## Purpose and authority
The adjacent `DYNAMIC-CONTENT-PORTFOLIO-REGISTRY-v1.json` is the compact **observed, read-only management index** of the curated accepted/usable content per family. It is **not** the new source of truth for a TSV, a semantic acceptance, a release, a Library file, an app runtime, or learner FSRS/SRS. Resolve the live source-owner LATEST/CHECKPOINT, user-approved exact TSV/ZIP, current Library/Drive bytes and app runtime pin independently. A newer accepted user artifact outranks stale Git. The seed records source-reported prior hashes, **not** new independent byte verifications. For Menschen B1, the current selected content is the user-accepted 2026-11-06 complete content ZIP; this still does not confer independent native Stage6 or global Stage7.

## Dynamic update contract
1. On each **new source review, enrichment, released successor, user acceptance, or explicit Control Center audit**, read the active repo bootstraps, central policy registry, project catalog, source-owned LATEST/CHECKPOINT, and its most recent accepted curated TSV/ZIP. Reconcile Library/Drive evidence; flag missing or moved files. An opened chat must re-resolve; old open chats are not updated in real time.
2. Separate `candidate`, `working`, `user_accepted_with_exceptions`, `content_final` and `runtime_final`. A new ZIP/date alone is **not** a promotion. Verify actual user acceptance or applicable gates, exact SHA, cards, source and stable IDs before updating the selected baseline. Never change another family.
3. **Compare-and-swap**: record expected immediate parent artifact SHA and Git owner-LATEST blob at the beginning of a change. Before publication re-fetch both; if either changed, **HOLD_CONCURRENT_UPDATE**, reconcile (never overwrite). For a new accepted baseline, append a small promotion receipt with `family_id`, `parent_sha256`, `successor_sha256`, `evidence`, `decision`, `date` and update only that family's entry.
4. Measure **delta** from the immediate accepted curated TSV, not the months-old publisher source. Review changed IDs, semantic dependencies and required structural/runtime gates; reuse still-valid evidence for unchanged rows. Never repopulate removed vocabulary for publisher fidelity.
5. If source Git LATEST is older than an accepted Library/Drive release, show `STALE_OWNER_POINTER`, do not downgrade. If current artifact cannot be verified, `HOLD_AUTHORITY_UNRESOLVED`. Do not substitute original PDFs.
6. Track content semantic/Stage4, packaged/Stage5, actual app import and persistence/Stage6, content-only Stage7 and **full runtime FINAL independently**. User-reported browser success is not independent native verification.
7. Git-only **read-only reconciliation runs on relevant GitHub push/PR events and on manual dispatch** through the scoped workflow. It reads pinned owner files from the checked-out branch, compares Git blobs and exact JSON pointers, writes derived CI artifacts only, and never promotes a release. This does **not** discover newer Library/Drive files, update running chats in real time, or act as a background Library watcher.
8. Keep historical accepted releases immutable and retain source-specific checkpoints. Do not delete Library/Drive files without explicit separate scope approval. No app UI, import, SRS, source or flashcard mutation from registry maintenance.

## Expansion and anti-churn
Use stable `family:<slug>` identifiers from `MASTER-PROJECT-CATALOG-v1.json`. New families (Aspekte, Grammar, Lesen/Schreiben) are added only after identifying their exact curated authority; do not manufacture CURRENT. Refresh a record on an actual decision/delta, not cosmetic report cycles. Compact `STATE.json` and the root catalog remain separate from the 10-family registry. No extra release ZIP is warranted.

**Initial inventory:** 10 families, 12,605 card records including cross-family overlap (unique deduplicated count unknown). The initial seed contains *no* source card edits and *no* native Stage4–7 acceptance promotions.

## Implemented Git source-pointer reconciler (v1)

- Program: `Tools/reconcile_dynamic_content_portfolio_v1.py`, using Python standard library and the ten registry-owned `owner_locator.artifact_sha_json_pointer` mappings. It verifies a canonical Git-blob SHA and the **selected artifact SHA field in the owner JSON** for each family.
- Trigger: `.github/workflows/dynamic-content-portfolio-reconcile.yml` on changes to registered sources / relevant workspaces and `workflow_dispatch`. Linux and Windows regression tests: `Verification/tests/test_dynamic_content_portfolio_reconciler_v1.py`. The CI job has read-only Git permissions and leaves outputs in GitHub Actions artifacts (14-day retention), not the source branch.
- Reports: `GIT_REFERENCES_MATCH__ARTIFACT_BYTES_UNCHECKED`, `OWNER_METADATA_DRIFT_REVIEW`, `OWNER_ARTIFACT_POINTER_DRIFT_REVIEW`, `OWNER_UNRESOLVED_HOLD`. A passing Git pointer is **not** a fresh physical ZIP readback nor proof that the owner knows of a newer Library/Drive accepted artifact.
- On any review/HOLD, return to the owner-specific accepted curated TSV, confirm the immediate parent and user decision, compare changed IDs, assess Stage4/5/6/7 separately, and publish a new immutable receipt with CAS. A reporting job NEVER calls the source writer or updates this registry.
- Local command: `python -B Tools/reconcile_dynamic_content_portfolio_v1.py --repo-root .`. To emit derived JSON/Markdown: `--out-dir <outside-repository-directory>`. Optional `--fail-on-review` is reserved for explicitly enforced review gates; the normal observation job is non-blocking.
- Remaining gap: a safe Library/Drive manifest resolver with real exact-byte evidence and user-accepted release precedence. Without that additional provider readback, the registry is **Git-reconciled**, not a fully live three-provider CURRENT resolver.

If that baseline advanced after this dated observation, require a new provider read; do not label an older snapshot a new file failure. No deletion, auto-promotion, ZIP repackaging or cross-family overwrite.
