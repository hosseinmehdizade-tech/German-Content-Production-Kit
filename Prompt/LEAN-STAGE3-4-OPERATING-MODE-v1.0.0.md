# Lean Stage 3/4 operating mode v1.0.0

**Status:** APPROVED operational simplification, prospective at the next SAFE editable workstream boundary (user approval 2026-11-02). This **replaces redundant operating steps**, not the v3.3.6 source/identity schema or the Stage 4/5/6/7 acceptance criteria. Historical original/LOCKED and committed source stay immutable.

## One reviewable card, one authoring pass

Stage 1 captures source once; Stage 2 resolves ID/occurrence once. Stage 3A inventory, 3B missing-value enrichment, and 3C disposition occur **in a single working pass on the exact mutable card**, reusing already-known data. Existing producers/consumers may still expect separate 3A/3B/3C fields/checkpoints: produce those **compatibility projections from the same working decision**, not another manual round or duplicate file. The 3A/3B/3C names and schema are not removed. If legacy writer/consumer cannot automatically emit equivalent output, retain its old adapter temporarily and do not declare full migration PASS. A current, completed facet may be reused; no forced repeated nine-facet prose checklists.

**Disposition default:** existing good content => `VERIFIED_PRESENT` (code `ALREADY_COVERED` for already-present useful combination); useful missing content => create after source/sense/provenance checks; no useful item => `CLOSED_NO_FORCE` with standardized nonempty reason (e.g., `NO_ADDITIONAL_TEACHING_VALUE`); truly not applicable => `NOT_APPLICABLE`; material uncertain provenance/sense => `HOLD`. No zero-item or fixed-density penalty. Machine-provided IDs, source SHA and already-verified lineage must be reused, not manually retyped for each field.


## Wortfamilie: one decision, two valid delivery representations (2026-11-03)

This is a clarification **inside the same Stage3/Stage4 process**, not an additional review/gate or a quota. Apply on the next safe editable lexical-card pass; leave historical LOCKED card/content bytes unchanged.

- The **typed canonical** relation `WORD_FAMILY` asserts an evidence-backed derivational family link. Use a real `target_id` only when that canonical lexical target is resolved; a similar meaning, shared topic, inflected form, or merely similar spelling is not sufficient. Unresolved freeform lexical family information must not be promoted into a fake target-ID relation.
- The **learner-visible** `Wortfamilie` details list is a text projection/gloss of useful family members. Existing useful freeform strings may be retained, with verified German/FA meaning, even when no stable target-ID exists. A typed `WORD_FAMILY` edge may instead be used in the Wortnetz/navigation view; therefore **not every typed edge must be duplicated as a physical Details line**. `Verwandt`/`RELATED`, Synonyme and Kombinationen remain separate semantic categories.
- In **one Stage3 pass**, reuse already known family members, exact source/sense, card ID, accepted translations and provenance. When a member exists in both representations, use one adjudication/evidence record, not two. Decisions are `VERIFIED_PRESENT`, justified `CLOSED_NO_FORCE`, `NOT_APPLICABLE` when appropriate, or `HOLD` for actual semantic/provenance uncertainty. No fixed number, no automatic word-formation guessing.
- Stage4 uses the same active independent risk-based review: high-risk false derivation, wrong sense/gloss or invented linkage gets individual challenge; low-risk unchanged families can reuse valid evidence or scoped family sampling. No new Wortfamilie-only Stage4 gate.
- Stage5 preserves the actual typed and visible fields already accepted; only project into a learner-visible section if the workstream's output contract requests it and the content/mapping is verified. Stage6 follows existing changed-feature checks and known-unavailable-browser policy, never inventing a native display PASS.
- **Approved bridge to Wortnetz (2026-11-03):** In the SAME existing Stage3 card decision ledger, a `word_family` or `wortfamilie` facet with `decision: VERIFIED_PRESENT` may carry already-reviewed `members` including exact `target_id`, `de` surface and existing registered `provenance.source_refs`. `Tools/bridge_verified_wortfamilie_to_wortnetz.py` uses this evidence **without another review gate**, pins the exact canonical source SHA, and produces an optional NEW canonical successor with one typed `WORD_FAMILY` edge for each unique, resolved, evidence-backed source-target pair. The existing `Tools/project_v411_vocabulary_cards.py` then projects it to `vnext_relations` and the existing Wortnetz uses it; reverse navigation is derived, never persisted as a second canonical edge. By default the bridge is a nonwriting dry run; `--apply` requires a separate output path, cannot overwrite input, and never edits app/runtime, LOCKED, user library, SRS or display sections. Unresolved identifiers, surface mismatch, missing source proof, HOLD, or absent family members leave verified freeform text unchanged. No automatic relation from string similarity or a forced 1:1 visual-text/graph parity; Stage4/5/6/7 acceptances still govern the eventual successor.
- **No extra command required for a compatible canonical Stage3 source:** the existing `Verification/emit_stage3_onepass_compat.py` writer now accepts optional `--wortnetz-successor NEW_CANONICAL.json` alongside its normal `--onepass`, `--current-bytes EXACT_CANONICAL.json`, and `--output 3ABC_VIEWS.json` arguments. The ledger pins exact working bytes; it emits the 3A/3B/3C views and safe successor from the same decisions in one execution. This is opt-in for canonical-registry streams and never a new mandatory gate; existing TSV-only pipelines are unaffected. The successor requires the usual independent downstream Stage4/5 acceptance before content-final promotion.
- `Verification/audit_wortfamilie_lean_views.py` is an **optional read-only mismatch diagnostic**. A visible-only or typed-only record is a review *candidate*, NOT automatically an error/blocked release. Only actual bad language, broken exact-ID linkage, duplicate display or loss under the intended consumer contract deserves correction. This does not mandate rerunning finished historical word-family batches.

## One independent quality challenge, not repeated editorial work

Stage 4 is the **already-active** `STAGE4-RISK-BASED-ACCEPTANCE-POLICY-v1.0.1.json` method:
- 100% automated structure, identity, DE/FA/EN completeness where required, source/provenance and full risk discovery.
- Every CRITICAL/HIGH *substantive* risk receives a distinct source-bound decision; unresolved CRITICAL/HIGH blocks PASS.
- MEDIUM/LOW/INFO scanner signals can use that policy's exact-ID family decisions and minimum independent representative challenge; unchanged unflagged items receive deterministic stratified samples. A flag is not automatically an error or a mandatory one-row editorial essay.
- Reuse valid reviews for unchanged source/content/dependency hashes. Revisit only changed IDs and affected dependencies, plus any proven systematic error family.
- Separate adversarial AI method for actual high-risk/sampled linguistic QA, with no fictional human signature. Stage 3 cannot self-certify Stage 4.

## Boundaries and compatibility

No change to source fidelity, original raw bytes, stable IDs, accepted translations, source claims, no-fabrication, exact CURRENT app/runtime, UI, SRS, anti-bypass Stage 5, actual Stage 6 browser verification or Stage 7 release. Corrections go into the exact current **mutable** authority with CAS and post-edit tests, not a report-only handoff; historical LOCKED uses an explicit successor. One bounded working authority, compact audit delta, milestone recovery; no per-item ZIP/review paperwork.

The previous `Prompt/KOMBINATIONEN-DIDACTIC-MEHRWERT-GATE-v1.0.0.md` scanner `--gate` **all-flags-individually-resolved** criterion is superseded for *new applicable* semantic decisions by the v1.1.0 didactic overlay below. The old portable kit, old tests and old receipts remain unchanged historical evidence, **not a second mandatory active gate**. A workflow using unmodified historical `--gate` may still fail on benign flags: this is a tooling compatibility LIMIT, not authority to fabricate approvals or silently skip a required integrity gate. Until that consumer is version-aware, report scoped migration pending; use the already-active risk-based Stage4 guard for new decisions. Do not claim the old scanner is physically patched.

Precedence for this narrow operating scope: user-approved active source/identity protection + v3.3.6 normative schema and the active Stage4 policy > **this lean Stage3 execution** > historical v1.0.0 didactic *per-advisory* gate and older nonactive Stage3/4 nine-manual-disposition drafts. Source-specific mandatory rules still apply where materially relevant. Other streams (Grammar, Lesen, Schreiben) inherit lexical Kombinationen only for standalone lexical cards.

**Rollout:** pilot a newly editable bounded lexical batch with exact parent+source hashes; demonstrate compatibility outputs and Stage4 risk evidence; then use the mode at subsequent safe boundaries. No mass rewrite, no retroactive Stage4 PASS, or required re-audit of unchanged historical completed streams without detected change/systemic failure.

## Implemented one-pass compatibility writer (2026-11-03)

Use `Verification/emit_stage3_onepass_compat.py` to derive 3A inventory, 3B deltas and 3C dispositions from ONE source-hash-bound ledger. Zero manual re-authoring rounds. The views preserve card IDs, existing decisions and unresolved HOLDs, and are explicitly `COMPATIBILITY_VIEW_NOT_OFFICIAL_STAGE_PASS`. Historical per-workstream receipt schemas differ: the converter does not invent their signed artifact metadata or replace unverified downstream serializers. Source-specific consumers can adapt their view mapping at a safe editable boundary; until proven, keep their existing validated serialization rather than falsely claiming native parity.
